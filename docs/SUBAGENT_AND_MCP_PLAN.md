# Subagent and MCP Plan

## Goal

Build Native Researcher into a local, tool-limited research system that can be
controlled through MCP. The long-term system should support specialized
subagents for literature discovery, abstract/full-text screening, scoring,
deduplication, and evidence retrieval without giving external models direct
permission to inspect or edit the source code.

The first production target is a topic-driven research workflow:

> Given a topic and criteria, find the most relevant biomedical papers across
> multiple databases, screen them with a dedicated model, score each paper
> against structured criteria, and return the best candidate set.

Example target task:

> Find docking papers for dopamine receptor D1 through D5 where docking was
> performed and an interaction map is present.

## Core Agents

### 1. Researcher Agent

The Researcher Agent owns the high-level research workflow.

Responsibilities:

- accept a user topic, target paper count, and optional inclusion/exclusion criteria
- convert the topic into structured search criteria
- generate comprehensive database-specific search queries
- search all enabled databases with a larger candidate window than the final requested count
- deduplicate and merge results across databases
- call the Screening Agent on the merged candidate set
- inspect screening scores and decide whether the initial search was broad enough
- expand or generalize the query if too few high-relevance candidates were found
- return a ranked result set with structured reasoning and trace metadata

Default behavior:

- target selected papers: `20`
- per-database initial fetch count: `target_count * 2`, so the default is `40`
- databases should be queried independently when enabled:
  - PubMed
  - PMC / Europe PMC
  - OpenAlex
  - CORE
  - arXiv
- if fewer than the required number of high-quality candidates remain after screening,
  the Researcher Agent should issue broader follow-up queries

The Researcher Agent should not directly perform low-level screening. It should
delegate structured article-level scoring to the Screening Agent.

### 2. Screening Agent

The Screening Agent owns article-level relevance scoring.

Initial input:

- topic
- criteria generated by the Researcher Agent
- candidate article metadata
- abstracts

Future input:

- extracted full text
- PDF sections
- figure/table captions
- methods/results passages

Responsibilities:

- inspect each candidate article independently
- return strict JSON
- score each criterion between `0.0` and `1.0`
- provide short evidence snippets or rationale for every score
- mark uncertainty explicitly
- avoid final claims that are not supported by the abstract or full text provided

Example criterion scores:

- `docking_performed`: `1.0` if explicit docking was done, `0.8` if highly likely,
  `0.0` if absent
- `interaction_map_present`: `1.0` if an interaction map or comparable ligand-residue
  interaction diagram is explicitly present, lower if only indirectly suggested
- `dopamine_receptor_d1_to_d5`: criterion-specific receptor coverage score
- `target_family_match`: dopamine receptor relevance
- `experimental_or_computational_context`: whether the paper contains usable methods

The Screening Agent model must be configurable from application settings. It
does not need to be the same model used by the chat assistant or researcher
planner.

## Relevance Scoring

Each paper receives per-criterion scores from the Screening Agent.

The backend computes a final normalized relevance score with a deterministic
formula. The proposed first version:

```text
final_relevance = sum(score_i ** 2 for score_i in criterion_scores) / number_of_criteria
```

This keeps the score in the `0.0` to `1.0` range and rewards articles that meet
multiple criteria strongly. Squaring makes weak evidence contribute less than
strong evidence.

Later versions can add:

- criterion weights
- hard gates for mandatory criteria
- confidence penalties
- database/source quality factors
- journal or citation enrichment
- recency preferences

## Candidate Search Flow

1. User submits topic and desired count.
2. Researcher Agent extracts structured criteria.
3. Researcher Agent creates database-specific query plans.
4. Backend searches each enabled database with `target_count * 2` results.
5. Backend normalizes and deduplicates candidates.
6. Screening Agent scores abstracts for all candidates.
7. Backend computes deterministic relevance score.
8. Researcher Agent reviews whether enough high-scoring candidates exist.
9. If not enough candidates pass the threshold, Researcher Agent broadens the query.
10. Backend repeats search, merge, dedupe, screen, and score.
11. Final ranked candidates are returned.

The backend should own deduplication, score computation, state persistence, and
policy enforcement. Agents should propose and evaluate, but deterministic
backend code should enforce the workflow rules.

## Query Expansion Policy

The first query should be comprehensive but still specific.

If high-quality candidates are fewer than the target count:

- relax phrase strictness
- add synonyms and alternative receptor names
- search by target family and ligand/domain terms
- broaden database-specific syntax
- increase candidate count if the database supports it safely
- avoid removing mandatory scientific concepts unless the Researcher Agent
  clearly marks the query as exploratory

For the dopamine docking example, possible expansion terms include:

- dopamine receptor D1, D2, D3, D4, D5
- DRD1, DRD2, DRD3, DRD4, DRD5
- molecular docking
- ligand docking
- interaction map
- interaction diagram
- ligand-residue interaction
- binding pocket
- molecular dynamics
- GPCR

Recommended schemas:

- `ResearchRun`
  - id
  - topic
  - target_count
  - status
  - created_at / updated_at
  - mode
  - selected_databases
  - screening_model
  - criteria
  - query_attempts

- `ResearchCriterion`
  - id
  - label
  - description
  - required
  - weight
  - scoring_guidance

- `CandidateArticle`
  - normalized id
  - DOI / PMID / PMCID / arXiv id / OpenAlex id / CORE id
  - title
  - abstract
  - authors
  - year
  - source databases
  - URLs
  - metadata

- `ScreeningResult`
  - candidate id
  - criterion scores
  - final relevance score
  - confidence
  - evidence snippets
  - rationale
  - model name
  - raw JSON

- `QueryAttempt`
  - database
  - query
  - requested count
  - returned count
  - normalized count
  - timestamp
  - error, if any

## Service Layer Additions

Before MCP, add a clean backend boundary:

- `ResearchFacade`
  - public entry point for MCP and API routes
  - calls search, dedupe, screening, scoring, and workspace services
  - hides internal service complexity from MCP

- `ResearchRunService`
  - persists run state
  - stores query attempts and candidate sets
  - resumes or inspects previous runs

- `CandidateSearchService`
  - runs multi-database searches
  - normalizes candidate records
  - applies per-database fetch limits

- `CandidateDedupService`
  - deduplicates by DOI, PMID, PMCID, title fingerprint, and source IDs
  - preserves all source provenance

- `ScreeningService`
  - chunks candidate abstracts
  - calls the selected screening model
  - validates strict JSON
  - retries invalid outputs safely

- `RelevanceScoringService`
  - computes deterministic final scores
  - applies weights, gates, and thresholds

- `MCPPermissionPolicy`
  - exposes only allowed tools for each MCP mode
  - prevents filesystem, shell, git, or source-code operations through MCP

## MCP Role

MCP should manage and expose the subagent workflows after the service boundary
exists. MCP clients should call high-level tools, not internal source modules.

Initial MCP tools:

- `native_researcher.health`
- `native_researcher.get_settings_summary`
- `native_researcher.start_research_run`
- `native_researcher.get_research_run`
- `native_researcher.list_research_runs`
- `native_researcher.screen_candidates`
- `native_researcher.search_literature`

Later MCP tools:

- `native_researcher.resolve_full_text`
- `native_researcher.screen_full_text`
- `native_researcher.extract_interaction_evidence`
- `native_researcher.export_research_report`

MCP clients should not receive:

- shell access
- git access
- direct filesystem access
- source-code editing tools
- access to `runtime/settings/`
- access to API keys or full local secrets

## MCP Modes

Default mode must be safe.

```text
readonly:
  - health
  - get_settings_summary
  - list_research_runs
  - get_research_run

research:
  - readonly tools
  - start_research_run
  - search_literature
  - screen_candidates
  - resolve_full_text, when implemented

admin:
  - research tools
  - settings updates
  - index rebuilds
  - maintenance tasks
```

`admin` must never be the default mode.

## Model Configuration

Add settings for:

- researcher planner model
- screening model
- full-text screening model
- max candidates per database
- default target count
- relevance threshold
- max query expansion attempts
- MCP mode

These settings should live under `runtime/settings/` or environment variables,
not in repository root files.

## Missing Risks And Design Questions

Before implementation, decide:

- Should the Researcher Agent be allowed to trigger PDF downloads automatically,
  or should PDF retrieval require explicit user approval?
- What is the minimum relevance threshold for the default result set?
- Which criteria are hard gates versus soft ranking signals?
- How should duplicate records with conflicting abstracts be merged?
- Should screening happen per database first or only after global deduplication?
- How many query expansion attempts should be allowed by default?
- How should failed database calls affect the final ranking?
- Should the Screening Agent provide calibrated probabilities or only heuristic
  scores?
- How should evidence snippets be verified when only abstracts are available?

## Recommended Implementation Order

1. Add schemas for research runs, criteria, candidates, query attempts, and
   screening results.
2. Add deterministic candidate deduplication.
3. Add `RelevanceScoringService` with the squared-score formula.
4. Add `ScreeningService` for abstract-only strict JSON screening.
5. Add configurable screening model settings.
6. Add `CandidateSearchService` for multi-database search with per-DB limits.
7. Add `ResearchRunService` and persist run state.
8. Add `ResearchFacade` as the only public orchestration boundary.
9. Add API routes for starting and inspecting research runs.
10. Add MCP permission policy and MCP docs/config examples.
11. Add MCP server tools that call `ResearchFacade`.
12. Add full-text/PDF screening after abstract screening is stable.

## First Milestone

The first useful milestone should be:

- topic input
- automatic criteria extraction
- multi-database abstract search
- deduplication
- abstract screening JSON
- deterministic relevance score
- top 20 ranked candidates
- stored research run trace

This milestone is enough to validate the subagent design before adding PDF
full-text analysis or external MCP clients.
